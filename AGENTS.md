# Coloring Tracker: архитектура и правила разработки

## Назначение

Это Telegram WebApp и мобильный веб‑трекер раскрасок. Django — источник истины
и административный каталог; Vue 3 — пользовательский интерфейс.
`legacy_kinopub/` — архив донора и не импортируется активным приложением.

## Активная структура

- `coloring_tracker/` — настройки, URL и Celery-конфигурация Django.
- `app/` — модели трекера, Django admin и JSON API.
- `frontend_webapp/` — Vue 3/Vite интерфейс.
- `tracker_bot/` — Telegram-бот, открывающий опубликованный WebApp.

Для локальной разработки Docker Compose запускает PostgreSQL, Redis, Django,
Vite, Celery и бота. Reverse proxy и туннелирование не используются. Для
проверки интерфейса используйте iframe-предпросмотр `/<telegram_id>/`.

## Доменная модель

1. `TrackerUser` — пользователь: Telegram `telegram_id` или временный `session_key`.
2. `ColoringBook` — книга каталога, которую редактирует только Django admin, либо личная книга с владельцем `TrackerUser`.
3. `ColoringPage` — работа с номером; разворот — одна запись с `spread_end`.
4. `UserBook` — книга в личной коллекции.
5. `ColoringWork` — завершённая работа с датой и необязательной фотографией.
6. `FavoriteBook` — сохранённая пользователем книга каталога.

Не используйте кино-термины (`Show`, `ViewUser`, `Wishlist`, `rating`) для
новых сущностей.

## Целостность данных

- Пользователь добавляет в коллекцию только опубликованные книги; каталог создаёт admin.
- Номер страницы уникален в книге; диапазоны страниц и разворотов не пересекаются.
- Разворот требует `spread_end > number`.
- Страница или разворот имеет только одну работу в рамках `UserBook`.
- При удалении работы удаляется её фотография.
- Повторная загрузка фото не меняет `completed_at`.

## Telegram-авторизация

- Фронтенд передаёт `Telegram.WebApp.initData` только в `X-Telegram-Init-Data`.
- Сервер проверяет Telegram HMAC до чтения `user.id`; токен — `TELEGRAM_BOT_TOKEN`.
- `initDataUnsafe.user` нельзя считать достоверным.
- Гостевая сессия допустима только для локального браузерного тестирования.
- Бот берёт адрес опубликованного приложения из `TELEGRAM_WEBAPP_URL`.

## API и интерфейс

- JSON API находится под `/api/tracker/`.
- Все клиентские запросы проходят через `frontend_webapp/src/api.js`.
- После изменения работы, избранного или коллекции перезагружайте данные из API.
- Тексты интерфейса — на русском; интерфейс — compact mobile-first.
- Важные фильтры и поиск отражайте в query-параметрах Vue Router.

## Локальная разработка

- Основной запуск: `docker compose up --build`.
- Django и Vite можно запускать на машине при локальных PostgreSQL и Redis.
- Локальный iframe-предпросмотр доступен по `http://localhost:8022/<telegram_id>/`.
- Production-сборка Vue использует Vite manifest; dev-режим включается `VITE_DEV_MODE=true`.

## Конфигурация и проверка

- Не коммитьте `.env`, `data/`, `node_modules/` и `dist/`.
- Для Telegram-бекапа задаются `TELEGRAM_BACKUP_ENABLED`,
  основной `TELEGRAM_BOT_TOKEN`, `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`.
  ID канала и стабильные параметры протокола хранятся в
  `coloring_tracker/backup_constants.py`.
- После изменения моделей выполняйте `python manage.py makemigrations app`.
- Перед сдачей запускайте:

  ```bash
  python manage.py check
  python manage.py makemigrations --check
  npm run build --prefix frontend_webapp
  docker compose config --quiet
  ```

## Визуальный стиль WebApp

Сохраняйте лёгкую пудрово-розовую тему с кремовыми акцентами, мягкими
градиентами, скруглёнными карточками и деликатным цветочным декором. Для пустой
обложки используйте `❀`. Контраст, фокус и нажимаемость на малых экранах важнее
декора.

## Новые пользовательские сценарии

- Фото работы, цветовой код и обложка личной книги перед отправкой проходят локальный редактор Vue: пользователь может менять масштаб, выделять область кропа, поворачивать изображение по часовой стрелке и сразу видеть результат. Редактор работает на локальном `File`/`Canvas`; после подтверждения сначала показывается оптимистичный локальный результат, а загрузка и фоновая синхронизация выполняются незаметно. При ошибке API нужно вернуть прежнее изображение и показать понятное сообщение. Клик или начало перетаскивания вне текущего выделения перемещает существующий кроп, не создаёт новый и не уменьшает его до нуля.
- Сервер не доверяет `accept="image/*"`: загружаемый файл проверяется Pillow и ограничивается по размеру. Обработанный браузером файл всё равно проверяется повторно перед сохранением.
- В каталоге есть кнопка «Предложить раскраску». Название обязательно; поле источника необязательно и намеренно хранится как произвольный текст, а не как `URLField` — пользователю разрешены сайт, комментарий или неполная ссылка. Максимальный размер нужен только как защита от злоупотребления; текст в Telegram экранируется как HTML и обрезается для лимита сообщения, полный вариант остаётся в админке.
- Предложение хранится в отдельной модели с привязкой к `TrackerUser`, отпечатком для защиты от повторов и серверным cooldown 30 секунд. Ограничения должны проверяться в транзакции с блокировкой пользователя; фронтенд не является механизмом защиты от спама.
- Telegram-уведомления отправляются Celery-задачей в `TELEGRAM_SUGGESTIONS_CHAT_ID`. Адрес конкретного объекта админки всегда строится из origin `TELEGRAM_WEBAPP_URL`; отдельная переменная для адреса админки не используется. В канал передаются экранированные имя, фамилия, username, название и источник в `<pre>`, а пользователь получает ссылку `tg://user?id=...`.
- Ответ пользователю отправляется из Django admin с флажком явной отправки. Поле ответа поддерживает Telegram HTML (`<b>`, `<i>`, `<u>`, `<s>`, `<code>`, `<pre>`, `<a href="...">`) и ограничивается лимитом Telegram; результат и ошибка отправки сохраняются в журнале предложения.

## Личные раскраски пользователя

- Личная раскраска хранится в той же модели `ColoringBook`, что и каталог, но имеет `owner=TrackerUser`, `is_published=False` и доступна только владельцу через его `UserBook`. Новые личные книги никогда не добавляются в каталог и не выдаются в `tracker_catalog` или `tracker_catalog_book_detail`.
- Создание выполняется через `POST /api/tracker/personal-books/` с названием, одним из `FLOWER_ICONS` и списком страниц. Название ограничено 255 символами; эмодзи не уникален и может повторяться в разных личных книгах.
- Страницы личной книги добавляются через `POST /api/tracker/personal-books/<user_book_id>/pages/`, удаляются через `DELETE .../pages/<page_id>/`. Нулевое количество страниц допустимо и при создании, и при сохранении настроек. Максимум — 300 физических страниц с учётом разворотов. Для разворота используется одна запись `ColoringPage` с `spread_end = number + 1`: разворот всегда состоит ровно из двух соседних страниц, а не из произвольного диапазона. Сервер повторно проверяет положительные номера, отсутствие пересечений и общий лимит 300 страниц.
- Настройки личной книги (название и эмодзи) изменяются через `PATCH /api/tracker/personal-books/<user_book_id>/`; удаление книги удаляет её страницы, работы, фотографии и цветовые коды. Все эти API проверяют владельца на сервере, а не только во Vue.
- Личная книга использует общий цикл работ: отметка готовности, фото, цветовой код, скрытие из отчёта и локальный редактор изображений. На карточке и в заголовке она явно помечается как «Личная» и отображается с выбранным эмодзи, но геометрия и порядок элементов должны быть такими же, как у обычной раскраски; отметка не должна сдвигать название.

## Редактирование изображений и feedback нажатия

- Сохранённые фото работы и цветовые коды можно открыть в `ImageEditor.vue` кнопкой «Изменить»: браузер загружает текущий файл в локальный `File`, после масштаба/кропа/поворота применяется существующая оптимистичная загрузка с откатом при ошибке.
- Для интерактивных элементов WebApp сохраняйте `-webkit-tap-highlight-color: transparent`, явный `:focus-visible` и короткое состояние `:active` с мягким масштабированием. Это относится не только к `button`, но и к кликабельным карточкам каталога и страниц; системная подсветка нажатия не должна проскакивать.

## UX личной раскраски и дизайн страниц

- В форме добавления личной раскраски количество страниц по умолчанию равно 50. Рядом доступны быстрые варианты 50 и 100; ручной ввод допускает пустое значение и `0`, верхняя граница — 300. Уменьшение числа строк не должно оставлять половину разворота.
- Каждая строка страницы имеет отдельное действие удаления. Удаление строки с разворотом удаляет обе физические страницы разворота; чтобы удалить только одну сторону, сначала отключают разворот, затем удаляют нужную страницу.
- Переключатель «Разворот из 2» объединяет текущую строку со следующей строкой и визуально оформляется как единая карточка. Обратное переключение разбивает её на две строки. Список использует короткую мягкую анимацию добавления, удаления и перемещения, без резких скачков высоты формы.
- Тексты-подсказки и `placeholder` (включая примеры вроде «Например…») должны быть заметно светлее введённого значения и не имитировать заполненные данные. Обязательные подписи, ошибки и кнопки сохраняют достаточный контраст.

## Предложения из каталога

- Подпись о том, что предложение можно отправлять раз в 30 секунд, в интерфейсе не показывается. Серверный cooldown 30 секунд и проверка в транзакции с блокировкой пользователя остаются обязательной защитой от спама.

## Production и релиз

### Production-профиль и доступ

- Production запускается тем же Docker Compose, но с production `.env`: `DEBUG=0`, корректные `ALLOWED_HOSTS`, HTTPS, закрытые от внешнего доступа PostgreSQL и Redis, а статические файлы и reverse proxy работают через production-конфигурацию проекта.
- Доступ к production: `ssh root@157.173.101.93`. Не подключаться к production, не читать его данные и не запускать там команды без явной просьбы пользователя на конкретную операцию.
- Явное разрешение на диагностику не разрешает выкладку, перезапуск, миграции, изменение конфигурации или другие изменения production. Для каждой такой операции нужно отдельное согласие.
- Перед релизом проверять healthcheck PostgreSQL, Redis и web-приложения; worker должен запускаться только после доступности инфраструктуры.
- Именованные тома PostgreSQL не удаляются обычным `docker compose down`.

### Релиз

- Миграции выполняются отдельным явным deploy-шагом до перезапуска web/worker, а не неявно каждым экземпляром web-процесса. Destructive restore на production DB не является smoke-тестом и без отдельного запроса не выполняется.
- Перед релизом проверять миграции, backend/Django checks, frontend build и Compose-конфигурацию. Базовый набор для этого проекта:

  ```powershell
  python manage.py check
  python manage.py makemigrations --check
  npm run build --prefix frontend_webapp
  docker compose config --quiet
  ```

- Проверки проекта по возможности выполнять внутри Docker Compose; локальное наличие Python-зависимостей на Windows не заменяет контейнерную проверку.
- Release запрещён, если секреты, `.env`, backup-файлы, ключи, реальные персональные данные или токены попали в Git, Docker-образы или обычные логи.
- После релиза проверить состояние сервисов, healthcheck web-приложения, доступность WebApp и работу worker/бота. При проблеме остановить дальнейшие изменения и сообщить пользователю, не выполняя самовольный rollback или восстановление базы.

### Порядок релиза

Незакоммиченные изменения на production не выкладываются. Нельзя использовать `scp`, `rsync`,
`sftp`, `docker cp` или эквивалентную прямую копировку файлов на сервер/в контейнер.
Если штатный remote/CI/release-механизм недоступен, остановиться и сообщить о блокере.

Релиз выполняется последовательно. Следующий шаг не выполнять, если предыдущий завершился ошибкой:

1. Проверить рабочее дерево, текущую ветку и отсутствие секретов/данных в изменениях. Релизить только явно согласованный набор изменений.
2. Выполнить проверки внутри локальных Docker Compose-сервисов: Django checks, проверку миграций, production-сборку frontend и `docker compose config --quiet`. Host `.venv` не считается заменой контейнерной проверки.
3. Проверить intended diff командами `git status` и `git diff --check`.
4. Сформировать commit со всем согласованным изменением и понятным сообщением. Если commit создать нельзя, остановиться и не обходить Git копированием файлов.
5. Отправить commit через обычный remote/release flow. Если проект подключит pull request или CI-деплой, использовать его и дождаться результата.
6. Получить отдельное явное согласие на production-выкладку, если оно не было дано в текущем запросе.
7. Подключиться к серверу командой `ssh root@157.173.101.93`, перейти в каталог production-копии `coloring-tracker` и обновить её только через fast-forward (`git pull --ff-only`). Не выполнять там команды в случайном каталоге.
8. Проверить, что production находится ровно на согласованном commit (`git rev-parse HEAD`), и только после этого собирать образы и перезапускать сервисы:

   ```powershell
   docker compose config --quiet
   docker compose build
   ```

9. До запуска web/worker выполнить миграции и подготовку Django через отдельный шаг Compose:

   ```powershell
   docker compose run --rm app-init
   ```

   В текущем Compose этот шаг также выполняет `collectstatic` и проверку/создание администратора; повторное выполнение должно быть идемпотентным.
10. Пересоздать затронутые сервисы и обновить стек без удаления именованных томов:

   ```powershell
   docker compose up -d --remove-orphans
   ```

11. Проверить состояние и healthcheck:

   ```powershell
   docker compose ps
   docker compose exec -T web python manage.py check
   ```

   Затем проверить доступность WebApp, worker, beat и Telegram-бота по их фактическим логам/healthcheck.
12. При ошибке остановить релиз, сохранить диагностику и сообщить пользователю. Самостоятельно не делать rollback, `docker compose down -v` или восстановление базы. В отчёте указать deployed commit и результат healthcheck.

### Docker Desktop из Codex на Windows

- Docker CLI установлен в `C:\Program Files\Docker\Docker\resources\bin`, а Compose работает через Docker Desktop named pipe. Ошибка `Access is denied` в обычном sandbox-shell не означает, что Docker недоступен.
- Перед выводом о недоступности Docker повторить команду из корня проекта с расширенным доступом Codex (`sandbox_permissions=require_escalated`) и явным вопросом-подтверждением пользователю.
- Базовые проверки выполнять из `D:\Root\Projects\coloring-tracker`:

  ```powershell
  docker compose ps
  docker compose config
  docker compose exec -T web python manage.py check
  ```

- Для команд через `exec_command` использовать префикс разрешения `["docker", "compose"]` либо более узкий префикс соответствующей команды. Не менять каталог или Compose-проект при повторной проверке доступа к Docker.
